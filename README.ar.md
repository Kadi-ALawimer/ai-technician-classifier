# مصنّف طلبات الفني بالذكاء الاصطناعي (AI Technician Request Classifier)

> هذه نسخة عربية من الملف الرئيسي [README.md](./README.md). النسخة الإنجليزية هي المرجع الأساسي والمحدّث دائمًا؛ هذه الترجمة للمراجعة السريعة.

تطبيق ويب مدعوم بالذكاء الاصطناعي يقرأ وصفًا نصيًا حرًا لمشكلة صيانة منزلية
(بالعربي أو الإنجليزي)، ويصنّفها حسب **الفئة** (سباكة، كهرباء، نجارة،
تكييف، عزل، أرضيات، أو غيرها) و**الأولوية** (عادي / عاجل)، وإذا كان النص
يصف أكثر من مشكلة مستقلة — يقسّمها تلقائيًا إلى طلبات منفصلة.

بُني كمشروع اختبار عملي لوظيفة **مطوّر تطبيقات ذكاء اصطناعي**. تم تصميمه
عن قصد ليكون صغيرًا وصحيحًا وسهل الشرح بمقابلة تقنية مباشرة، بدلًا من أن
يكون مثقلًا بالمزايا.

## 1. نظرة عامة على المشروع

يكتب العميل وصف مشكلة مثل:

> "عندي تسريب مويه في المطبخ والكهرباء مقطوعة في غرفة النوم"

يرسل الباك اند هذا النص لنموذج لغوي (LLM) مع تعليمات صارمة بأن يرجّع
**JSON منظم فقط**. يقسّم الذكاء الاصطناعي النص إلى مشاكل مستقلة ويصنّف كل
واحدة:

```json
{
  "requests": [
    { "problem": "تسريب مويه في المطبخ", "category": "plumbing", "priority": "urgent" },
    { "problem": "الكهرباء مقطوعة في غرفة النوم", "category": "electrical", "priority": "normal" }
  ]
}
```

يراجع المستخدم النتيجة، ويقدر يعدّل الفئة/الأولوية لأي عنصر، يؤكد، ويُحفظ
الطلب بقاعدة البيانات. صفحة ثانية تعرض كل الطلبات المحفوظة.

## 2. المزايا

- تحليل المشكلة باللغة الطبيعية **بالعربي والإنجليزي**.
- **تقسيم تلقائي** للرسالة الواحدة إلى عدة طلبات مستقلة.
- **فئة** و**أولوية** قابلتان للتعديل قبل الحفظ (الذكاء الاصطناعي يقترح،
  والإنسان يؤكد).
- مزود ذكاء اصطناعي قابل للتبديل: **mock** (بدون مفتاح API)، **Gemini**،
  أو **OpenAI**.
- **تحقق صارم من جهة السيرفر** لكل حقل (لا يثق أبدًا بالذكاء الاصطناعي أو
  الواجهة بشكل أعمى).
- واجهة متجاوبة (Responsive) وأولوية للجوال، مع حالات تحميل/خطأ/فراغ.
- إنشاء تلقائي لقاعدة بيانات SQLite عند أول تشغيل.
- مجموعة اختبارات آلية أساسية للباك اند (pytest).

## 3. التقنيات المستخدمة

| الطبقة | التقنية | ملاحظات |
|---|---|---|
| Frontend | React 18 + Vite + **TypeScript** | تصميم متجاوب بأولوية للجوال، بدون إطار عمل واجهة (UI framework) |
| Backend | Python 3.11+ + **FastAPI** | غير متزامن (Async)، تحقق عبر Pydantic |
| AI | **Gemini** أو **OpenAI** (قابل للتبديل) + مزود **Mock** | مخرجات JSON منظمة |
| قاعدة البيانات | **SQLite** + SQLModel (SQLAlchemy 2.0 + Pydantic) | تُنشأ تلقائيًا عند أول تشغيل |
| نمط الـ API | **REST** (JSON عبر HTTP) | 4 نقاط وصول فقط |
| الاختبار | **pytest** | يعمل على مزود mock، بدون حاجة لمفتاح API |

راجع [القرارات التقنية](#18-القرارات-التقنية) لمعرفة سبب كل اختيار من هذه
الاختيارات.

## 4. البنية المعمارية

```
┌─────────────┐      POST /api/analyze       ┌──────────────┐      ┌──────────────┐
│   React     │ ───────────────────────────► │   FastAPI    │ ───► │  AI Service  │
│  (Vite,TS)  │                               │   Backend    │      │   (Gemini /  │
│             │ ◄─────────────────────────── │              │ ◄─── │  OpenAI /    │
└─────────────┘   { requests: [...] }         └──────────────┘      │   Mock)      │
      │                                              │               └──────────────┘
      │  المستخدم يراجع ويعدّل                        │
      │  POST /api/requests                          ▼
      └──────────────────────────────────────►  ┌──────────┐
                                                  │  SQLite  │
                                                  └──────────┘
```

فصل صارم للمسؤوليات:

- **الواجهة (React)** تتكلم فقط مع الباك اند الخاص بنا. لا تستدعي
  Gemini/OpenAI مباشرة أبدًا، ولا ترى مفتاح API أبدًا.
- **الباك اند (FastAPI)** يملك كل التحقق والتنسيق والوصول لقاعدة
  البيانات.
- **خدمة الذكاء الاصطناعي (AI Service)** طبقة معزولة
  (`app/services/ai_service.py` + `app/services/providers/*`). المسارات
  (routes) لا تستدعي SDK/API أي مزود مباشرة أبدًا — تستدعي فقط
  `analyze_request()`.
- **قاعدة البيانات (SQLite)** لا يُكتب فيها إلا بعد تأكيد المستخدم.

نفّذ هذي الأوامر **بالترتيب**، من تيرمنال PowerShell داخل VS Code.

لو استلمت هذا المشروع كمجلد/ملف مضغوط، فك الضغط وافتح المجلد بـ VS Code
(`File > Open Folder`). بعدها افتح تيرمنال وانتقل للخطوة 7.2.

لو تبدأ من الصفر:

```powershell
mkdir ai-technician-classifier
cd ai-technician-classifier
```

(بعدها ضع `frontend/`، `backend/`، `.gitignore`، و`README.md` بهذا
المجلد)

### 7.2 إعداد الباك اند

```powershell
cd backend
python -m venv .venv
.venv\Scripts\Activate.ps1
```

> لو حجب PowerShell سكربت التفعيل برسالة "execution policy"، نفّذ هذا مرة
> وحدة (كمستخدم عادي، مو Admin):
> `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`، بعدها أعد تشغيل
> أمر `Activate.ps1`.

```powershell
pip install -r requirements.txt
copy .env.example .env
```

ملف `.env` الافتراضي يستخدم `AI_PROVIDER=mock`، فالباك اند يشتغل مباشرة
**بدون أي مفتاح API**. راجع [وضع الذكاء الاصطناعي الحقيقي](#12-وضع-الذكاء-الاصطناعي-الحقيقي)

```powershell
copy .env.example .env
```

ملف `.env` الخاص بالفرونت إند يحدد فقط رابط الباك اند — أبدًا ما يحتوي

## 11. وضع الذكاء الاصطناعي التجريبي (Mock)

مع `AI_PROVIDER=mock` (الافتراضي)، ما تحتاج مفتاح API ولا اتصال إنترنت.
مصنّف بسيط قائم على قواعد يحاكي الذكاء الاصطناعي عشان يشتغل التطبيق كامل
من البداية للنهاية. يعالج بشكل صحيح أمثلة المواصفة الأصلية:

| المدخل | المخرج |
|---|---|
| "water leak in kitchen" | plumbing / urgent |
| "AC is not cooling" | ac / normal |
| "power is out in bedroom" | electrical / normal |
| "water leak in kitchen and electricity is out in bedroom" | طلبان: plumbing/urgent، electrical/normal |
| "عندي تسريب مويه في المطبخ والكهرباء مقطوعة في غرفة النوم" | طلبان: plumbing/urgent، electrical/... |

مزود الـ mock موجود بالكامل بملف
`backend/app/services/providers/mock_provider.py`. منطقه بسيط قائم على
كلمات مفتاحية/قواعد **بشكل متعمد** — دوره فقط أن يكون بديلًا لنموذج لغوي
حقيقي أثناء التطوير والعروض؛ راجع
[الـ Prompt والمخرجات المنظمة](#15-الـ-prompt-والمخرجات-المنظمة) لمعرفة
كيف يفهم المزودان الحقيقيان المعنى فعليًا بدل الكلمات المفتاحية.

## 12. وضع الذكاء الاصطناعي الحقيقي

### الخيار أ — Gemini (موصى به: باقة مجانية سخية، سريع، REST API بسيط)

1. روح لـ **Google AI Studio** (`https://aistudio.google.com`)، سجّل
   دخول بحساب جوجل.
2. اضغط **"Get API key"** ← **"Create API key"**.
3. انسخ المفتاح المُولَّد.
4. بملف `backend/.env`:
   ```
   AI_PROVIDER=gemini
   GEMINI_API_KEY=مفتاحك_الحقيقي_هنا
   ```
5. أعد تشغيل الباك اند (`Ctrl+C`، ثم `uvicorn app.main:app --reload`
   مرة ثانية).

### الخيار ب — OpenAI

1. روح لـ `https://platform.openai.com/api-keys`، سجّل دخول.
2. اضغط **"Create new secret key"**، وانسخه (ما تقدر تشوفه مرة ثانية).
3. بملف `backend/.env`:
   ```
   AI_PROVIDER=openai
   OPENAI_API_KEY=مفتاحك_الحقيقي_هنا
   ```
4. أعد تشغيل الباك اند.

**لا ترفع أبدًا مفتاحًا حقيقيًا لـ git.** ملف `backend/.env` مستثنى من
git خصيصًا لمنع هذا. فقط `backend/.env.example` (بقيم فارغة) موجود
بالمستودع.

**ليش Gemini بدل OpenAI بهذا المشروع؟** الاثنان يشتغلان بنفس الكفاءة عبر
هذا الكود (تغيير المزود مجرد سطر واحد بمتغير بيئة). اخترت Gemini كتوصية
أساسية لأن باقته المجانية وقت كتابة هذا المستند كانت سخية بما يكفي لتشغيل
كامل هذا الاختبار بدون حساب فوترة — مناسب لاختبار عملي عن بُعد. لو عندك
رصيد OpenAI، `AI_PROVIDER=openai` يشتغل بنفس الطريقة تمامًا.

## 13. نقاط الوصول (API Endpoints)

الرابط الأساسي: `http://localhost:8000`

### `GET /api/health`
فحص أن الخدمة تعمل.
```json
{ "status": "ok", "ai_provider": "mock" }
```

### `POST /api/analyze`
يصنّف نصًا حرًا إلى طلب واحد أو أكثر منظم. **لا** يحفظ أي شيء بقاعدة
البيانات.

الطلب:
```json
{ "description": "عندي تسريب مويه في المطبخ والكهرباء مقطوعة في غرفة النوم" }
```

الاستجابة `200`:
```json
{
  "requests": [
    { "problem": "تسريب مويه في المطبخ", "category": "plumbing", "priority": "urgent" },
    { "problem": "الكهرباء مقطوعة في غرفة النوم", "category": "electrical", "priority": "normal" }
  ]
}
```

الأخطاء: `422` (وصف فارغ/قصير جدًا/طويل جدًا)، `502` (فشل مزود الذكاء
الاصطناعي أو رجّع استجابة غير قابلة للاستخدام).

### `POST /api/requests`
يحفظ طلبًا مصنّفًا واحدًا (ربما عدّله المستخدم).

الطلب:
```json
{ "problem": "تسريب مويه في المطبخ", "category": "plumbing", "priority": "urgent" }
```

الاستجابة `201`:
```json
{
  "id": 1,
  "problem": "تسريب مويه في المطبخ",
  "category": "plumbing",
  "priority": "urgent",
  "created_at": "2026-09-14T10:15:00Z"
}
```

الأخطاء: `422` لو `category`/`priority` مو من القوائم الثابتة، أو
`problem` فارغ/طويل جدًا.

### `GET /api/requests`
يرجّع كل الطلبات المحفوظة، الأحدث أولًا.

## 14. قاعدة البيانات

- **المحرك:** SQLite (قائم على ملف، بدون إعداد — مناسب لحجم هذا المشروع؛
  راجع [القرارات التقنية](#18-القرارات-التقنية)).
- **ORM:** SQLModel (مبني على SQLAlchemy 2.0 + Pydantic).
- **الجدول:** `request`

| العمود | النوع | ملاحظات |
|---|---|---|
| `id` | integer | مفتاح أساسي، يزيد تلقائيًا |
| `problem` | string | نص المشكلة (بحد أقصى 500 حرف) |
| `category` | enum | واحدة من 7 فئات ثابتة |
| `priority` | enum | `normal` \| `urgent` |
| `created_at` | datetime | يُضبط تلقائيًا (UTC) عند الإدراج |

- **التهيئة:** `app/database/db.py::create_db_and_tables()` يعمل عند كل
  بدء تشغيل للباك اند (عبر `lifespan` بـ FastAPI). ينشئ مجلد `data/`
  وملف `app.db` تلقائيًا لو ما كانا موجودين — **لا تحتاج خطوة ترحيل
  (migration) يدوية** لمشروع بهذا الحجم. (نظام إنتاجي حقيقي سيضيف
  ترحيلات Alembic بمجرد ما يحتاج المخطط (schema) يتطور بأمان مع بيانات
  موجودة — راجع [تحسينات مستقبلية](#21-تحسينات-مستقبلية)).

## 15. الـ Prompt والمخرجات المنظمة

نص الـ prompt كامل موجود بملف `backend/app/services/prompts.py`
(`SYSTEM_PROMPT`). ملخص لما يطلبه من النموذج:

1. قراءة رسالة العميل (عربي، إنجليزي، أو مزيج).
2. لو وصفت **أكثر من مشكلة مستقلة**، يقسّمها لعناصر منفصلة — أبدًا ما
   يدمج مشكلتين مختلفتين، وأبدًا ما يقسّم مشكلة واحدة لأجزاء.
3. تصنيف كل واحدة ضمن 7 فئات بالضبط (`other` لو غير واضحة — أبدًا ما
   يخترع فئة جديدة).
4. تصنيف كل واحدة كـ `urgent` فقط لو فيه خطر حقيقي من ضرر، إصابة، أو
   حالة طارئة فعلية (غرق، أسلاك مكشوفة/تشرر شرر، رائحة غاز، عطل تكييف
   خطير)؛ وكل شي غير ذلك `normal`.
5. الإبقاء على نص `problem` باللغة اللي استخدمها العميل (بدون ترجمة).
6. **الرد بـ JSON فقط** — بدون شرح، وبدون علامات markdown.

**فرض البنية، مرتين:**
- *على مستوى المزود:* Gemini يستخدم `responseSchema` +
  `responseMimeType: application/json`؛ OpenAI يستخدم Structured Outputs
  (`response_format: json_schema`، `strict: true`). كلاهما يقيّد مخرجات
  النموذج وقت التوليد.
- *على مستوى الباك اند (شبكة الأمان الحقيقية):* بغض النظر عمّا يعِد به
  المزود، ملف `ai_service.py` يتحقق من كل استجابة مقابل سكيما Pydantic
  الخاصة بنا (`AnalyzeResponseOut`) قبل ما تقترب من الواجهة أو قاعدة
  البيانات. فئة غير صحيحة، حقل ناقص، أو JSON مشوّه — كلها تُكتشف هنا
  وتتحول لخطأ `502` نظيف — لا تمر أبدًا.

## 16. اعتبارات الأمان

- **مفاتيح API أبدًا ما تصل للواجهة الأمامية.** تُقرأ فقط من
  `backend/.env` عبر `pydantic-settings`. ملف `.env` الخاص بالفرونت إند
  يحتوي فقط على `VITE_API_BASE_URL` — بما إن Vite يكشف أي متغير يبدأ بـ
  `VITE_` لحزمة المتصفح، فمفتاح API أبدًا ما يجب أن يبدأ بهذا الشكل (أو
  يُوضع بكود الفرونت إند أصلًا).
- **CORS محدود** فقط لمصادر الفرونت إند المحلية المعروفة
  (`http://localhost:5173`) — مو `allow_origins=["*"]`.
- **التحقق من جهة السيرفر هو مصدر الحقيقة.** كل حقل (`category`،
  `priority`، أطوال النصوص) يُعاد التحقق منه عبر FastAPI/Pydantic
  بالباك اند، بغض النظر عمّا تحقق منه الفرونت إند مسبقًا أو ما رجّعه
  الذكاء الاصطناعي.
- **لا تُرسل أي تفاصيل خطأ تقنية (stack traces) للعميل أبدًا.** معالج
  استثناءات عام بملف `main.py` يمسك أي خطأ غير متوقع ويرجّع رسالة عامة
  `500`؛ الأخطاء المتوقعة والمحددة (رد سيء من الذكاء الاصطناعي، خطأ
  بقاعدة البيانات) ترجّع رسائل قصيرة ونظيفة. التفاصيل الكاملة تُكتب فقط
  بسجلات السيرفر.
- **ملفات `.env` مستثناة من git**؛ فقط `.env.example` (بدون أسرار)
  مضمّن بالمستودع.

## 18. القرارات التقنية

مكتوبة بالطريقة اللي تشرحها لمُقابِلك — مختصرة وصادقة، بدون تبريرات
مبالغ بتعقيدها.

- **React + Vite، بـ TypeScript (مو JavaScript عادي):** Vite يعطي بدء
  تشغيل شبه فوري للسيرفر التطويري (dev server) وتحديث حي (HMR)، وهذا
  مهم لاختبار قصير المدة. اخترت TypeScript على JS العادي لأن الفرونت
  إند والباك اند يتشاركان عقد بيانات دقيق (تعدادات الفئة/الأولوية،
  أشكال الطلبات) — الأنواع (types) تمسك خطأ إملائي مثل `"eletrical"`
  وقت الترجمة (compile) بدل ما يصير خطأ وقت التشغيل، وتعطي انطباع أكثر
  احترافية بالمراجعة بدون إضافة تعقيد حقيقي لمشروع بهذا الحجم.
- **FastAPI (مو Flask/Django):** تكامل أصلي مع Pydantic يعطي تحقق
  الطلب/الاستجابة "مجانًا" (مهم هنا لأن التحقق من مخرجات الذكاء
  الاصطناعي هو صلب الموضوع)، توثيق OpenAPI تلقائي بمسار `/docs`، ودعم
  غير متزامن (async) لاستدعاء واجهات ذكاء اصطناعي خارجية بكفاءة.
- **SQLite (مو PostgreSQL):** بدون إعداد — بدون سيرفر قاعدة بيانات
  منفصل يحتاج تثبيت/تشغيل لمشروع اختبار. نفس كود SQLAlchemy/SQLModel
  بكلا الحالتين، فالتبديل لـ PostgreSQL لاحقًا مجرد تغيير سطر واحد
  بـ `DATABASE_URL`، مو إعادة كتابة.
- **SQLModel:** يجمع تعريف جدول SQLAlchemy ونموذج تحقق Pydantic بصف
  واحد، وهذا يقلل الكود المكرر لمشروع فيه كيان بسيط واحد (`Request`).
- **REST، مو GraphQL:** ثلاثة موارد بسيطة، بدون استعلامات متداخلة
  معقدة — REST هو أبسط حل يناسب وهو الأكثر توقعًا بأجواء المقابلة.
- **مخرجات JSON منظمة من النموذج اللغوي:** مخرجات نصية حرة كانت
  ستحتاج تحليل نصوص/regex هش. المخرجات المنظمة (مقيدة بسكيما على
  مستوى المزود، ثم يُعاد التحقق منها بـ Pydantic) تجعل استجابة الذكاء
  الاصطناعي موثوقة مثل أي API نمطي آخر.
- **متغيرات بيئة للإعدادات (مو قيم مكتوبة مباشرة بالكود):** ممارسة
  قياسية (12-factor) — تسمح لنفس الكود يشتغل بوضع mock، أو مع Gemini،
  أو مع OpenAI، وتبقي الأسرار خارج نظام التحكم بالإصدارات.
- **مزود Mock منفصل:** يسمح للتطبيق كامل (فرونت إند، باك اند، قاعدة
  بيانات، اختبارات، CI) يشتغل ويُعرض بدون أي مفاتيح API وبدون تكلفة،
  ويجعل تجريد طبقة خدمة الذكاء الاصطناعي (واجهة `AIProvider`) واضحًا
  وقابلًا للاختبار.

### أسئلة متوقعة من المقابِل — إجابات قصيرة وصادقة

**ليش React؟**
معيار صناعي، نموذج المكونات (component model) يناسب هذي الواجهة (نموذج
+ قائمة) بشكل جيد، وأردت أداة بناء (Vite) بتكرار تطوير محلي سريع لاختبار
محدد بوقت.

**ليش FastAPI؟**
تكامل أصلي مع Pydantic (مهم لأني أتحقق من مخرجات ذكاء اصطناعي غير
موثوقة)، توثيق تفاعلي تلقائي، ودعم async لاستدعاء واجهات ذكاء اصطناعي
خارجية بدون حظر (blocking).

**ليش SQLite؟**
بدون إعداد لمشروع بهذا الحجم — بدون سيرفر قاعدة بيانات يحتاج تثبيت. نفس
كود SQLAlchemy/SQLModel بكلا الحالتين، فالانتقال لـ PostgreSQL لاحقًا
تغيير إعداد، مو إعادة كتابة.

**ليش حطيت مفتاح API بالباك اند؟**
أي شي يُرسل للمتصفح (بما فيه متغيرات Vite اللي تبدأ بـ `VITE_`) مرئي
علنًا بحزمة JS المترجمة. أي مفتاح هناك يقدر أي شخص يستخرجه ويستخدمه
بحسابي/فاتورتي. الباك اند هو البيئة الموثوقة الوحيدة، فهو المكان الوحيد
اللي يرى المفتاح.

**ليش ما تستدعي الذكاء الاصطناعي مباشرة من React؟**
نفس سبب كشف المفتاح أعلاه، بالإضافة إنه يعني الفرونت إند ما يقدر يفرض
تحقق أو قواعد عمل — الباك اند لازم يكون مصدر الحقيقة الوحيد لما هو
"صحيح" من بيانات أصلًا، فيجب يملك استدعاء الذكاء الاصطناعي أيضًا.

**كيف يقسّم الذكاء الاصطناعي عدة مشاكل؟**
الـ prompt يوجّهه صراحة: لو وصفت الرسالة أكثر من مشكلة مستقلة، يرجّع
عناصر متعددة بمصفوفة `requests`، عنصر لكل مشكلة، وأبدًا ما يدمج أو
يفرط بالتقسيم. النموذج يفكر بهذا دلاليًا (semantically)، مو بمطابقة
كلمات مفتاحية (هذي طريقة مزود الـ *mock* فقط، كبديل — المزودان
الحقيقيان يفهمان المعنى).

**كيف تتحقق من استجابة الذكاء الاصطناعي؟**
طبقتان: يُطلب من المزود مخرجات مقيدة بسكيما (Gemini `responseSchema` /
وضع OpenAI الصارم `json_schema`)، وبعدين، بغض النظر عن ذلك، الباك اند
يحلل الـ JSON ويتحقق منه مقابل نموذج Pydantic (`AnalyzeResponseOut`)
بحقول `category`/`priority` مقيدة بتعدادات (enums). أي شي ما يطابق
يُرفض قبل ما يوصل للمستخدم.

**وش يصير لو رجّع الذكاء الاصطناعي JSON غير صحيح؟**
`json.loads()` (أو تحليل المزود) يفشل، يُمسك، يُسجّل، ويتحول لخطأ عام
`AIServiceError` ← الـ API يرجّع `502` برسالة قصيرة آمنة للمستخدم.
ما يوصل للفرونت إند أي خطأ خام أو تفاصيل تقنية.

**كيف تتعامل مع فشل الـ API (انقطاع شبكة، تعطل المزود)؟**
كل استدعاء لمزود مغلّف بـ try/except يرفع `AIProviderError` واحد؛
`ai_service.py` يمسكه ويرفع `AIServiceError`؛ المسار (route) يمسكه ويرجّع
`502` برسالة واضحة. الفرونت إند يمسك الخطأ من `fetch` ويعرضه بصندوق
تنبيه بدل ما ينهار.

**كيف تحسّن هذا النظام للإنتاج؟**
أضيف مصادقة، أنتقل لـ PostgreSQL، أضيف تحديد معدل (rate limiting) على
`/api/analyze` (استدعاءات النموذج اللغوي تكلف مال)، أضيف تجميع مراقبة/
سجلات، وأبني مجموعة بيانات تقييم صغيرة لتتبع دقة التصنيف عبر الزمن بدل
التقييم بالعين.

**ليش استخدمت مخرجات JSON منظمة بدل تحليل نص حر؟**
النص الحر كان سيحتاج تحليل regex/NLP هش من جهتي، ويتعطل بشكل غير متوقع.
المخرجات المنظمة تجعل النموذج اللغوي يتصرف مثل أي API نمطي آخر أتكامل
معه.

**كيف تمنع حقن الأوامر (Prompt Injection)؟**
نص المستخدم يُدرج بالـ prompt فقط كـ *بيانات* (ملفوف بكتلة محددة بوضوح،
مثل `"""..."""`)، وأبدًا ما يُدمج بالتعليمات. مخرجات النموذج مقيدة
بسكيما ويُعاد التحقق منها بشكل مستقل، فحتى لو حاول أحد يحقن تعليمات
بوصف مشكلته، أسوأ سيناريو هو طلب مُصنَّف بشكل خاطئ — مو تنفيذ كود أو
استجابة معطوبة — لأن أي شي من الذكاء الاصطناعي أبدًا ما يُوثق به بما
يكفي ليُنفَّذ أو يتجاوز التحقق.

**كيف تقيّم دقة تصنيف الذكاء الاصطناعي؟**
أبني مجموعة بيانات معنونة صغيرة من أوصاف واقعية مع فئتها/أولويتها
الصحيحة، أشغّلها بالمصنّف، وأحسب الدقة/الضبط لكل فئة. أتتبع ذلك عبر
الزمن مع تغيّر الـ prompt أو النموذج، بدل الاعتماد على فحوصات يدوية
عشوائية.

**كيف تدعم العربي بشكل أفضل؟**
أختبر بلهجات إقليمية حقيقية وصياغات غير رسمية (مو بس العربية الفصحى)،
وممكن أضبط الـ prompt أو أضيف أمثلة عربية محددة (few-shot) لو ظهرت دقة
أضعف بالنصوص العامية.

**كيف توسّع التطبيق؟**
أنقل قاعدة البيانات لـ PostgreSQL مع تجميع اتصالات (connection pooling)،
أضع الباك اند خلف عدة نسخ عديمة الحالة (stateless) خلف موزّع أحمال
(already stateless — بدون حالة جلسة بالذاكرة)، أضيف تخزين مؤقت
للاستدعاءات المتكررة/المتشابهة، وأنتقل لطوابير مهام غير متزامنة لو صار
زمن استجابة الذكاء الاصطناعي عنق زجاجة لمعدل الطلبات.

**ليش بنيت طبقة خدمة ذكاء اصطناعي بدل استدعاء Gemini/OpenAI مباشرة
بالمسار؟**
فصل المسؤوليات: المسار ما يحتاج يعرف أي مزود نشط، ولا كيف يبني حمولة
طلب ذلك المزود المحددة، ولا كيف يحلل شكل استجابته المحدد. هذا أيضًا يجعل
تبديل المزود سهلًا جدًا (متغير بيئة واحد) وقابلًا للاختبار (مزود الـ
mock مجرد تطبيق آخر لنفس الواجهة).

**وش كنت بتغيّر لو صار عند التطبيق مليون مستخدم؟**
واقعيًا: PostgreSQL مع نسخ قراءة (read replicas)، توسيع أفقي للباك اند،
طابور رسائل بين الـ API واستدعاء الذكاء الاصطناعي (عشان استجابة نموذج
بطيئة ما تُبقي اتصال HTTP مفتوحًا)، تخزين مؤقت قوي للمدخلات المتكررة،
تحديد معدل لكل مستخدم، واهتمام أكبر بتكلفة مزود الذكاء الاصطناعي — لأنها
تصير التكلفة المهيمنة على التوسع، مو الحوسبة.

## 24. تعديلات محتملة أثناء البرمجة الحية

خمس تعديلات صغيرة وواقعية ممكن يطلبها المقابِل، ومكان كل واحد بالضبط.

### 1. إضافة فئة جديدة (مثلًا "landscaping" - تنسيق حدائق)

- `backend/app/models/enums.py` — أضف `LANDSCAPING = "landscaping"` لـ
  `Category`.
- `backend/app/services/prompts.py` — أضف `"landscaping"` لـ
  `ALLOWED_CATEGORIES` واذكرها بقائمة/قواعد الفئات بالـ prompt.
- `frontend/src/types/index.ts` — أضف `"landscaping"` لمصفوفة
  `CATEGORIES` وتسمية بـ `CATEGORY_LABELS`.
- هذا كل شي — القائمة المنسدلة، التحقق، والـ prompt كلها تلتقطها تلقائيًا
  لأن كل شي يقرأ من هاتين القائمتين.

### 2. تغيير منطق "عاجل" (urgent)

- القواعد اللي يتبعها الذكاء الاصطناعي موجودة بـ `SYSTEM_PROMPT` بملف
  `backend/app/services/prompts.py` (عدّل نقطة "urgent").
- القاعدة المكافئة بمزود الـ mock هي `_URGENT_KEYWORDS` وحالة التسريب
  الخاصة بالسباكة بملف
  `backend/app/services/providers/mock_provider.py`.

### 3. إضافة نقطة وصول `DELETE /api/requests/{id}`

بملف `backend/app/api/routes_requests.py`، أضف:

```python
@router.delete("/requests/{request_id}", status_code=204)
def delete_request(request_id: int, session: Session = Depends(get_session)) -> None:
    db_request = session.get(RequestModel, request_id)
    if not db_request:
        raise HTTPException(status_code=404, detail="Request not found.")
    session.delete(db_request)
    session.commit()
```

بعدها أضف زر "Delete" بملف `frontend/src/pages/RequestsPage.tsx` يستدعي
دالة جديدة `deleteRequest(id)` بملف `frontend/src/services/api.ts`،
ويحذف ذلك العنصر من الحالة المحلية عند النجاح.

### 4. إضافة فلتر لـ `GET /api/requests` (مثلًا `?category=plumbing`)

بملف `backend/app/api/routes_requests.py`:

```python
@router.get("/requests", response_model=list[RequestOut])
def list_requests(
    category: Category | None = None,
    session: Session = Depends(get_session),
) -> list[RequestModel]:
    statement = select(RequestModel).order_by(RequestModel.created_at.desc())
    if category:
        statement = statement.where(RequestModel.category == category)
    return list(session.exec(statement).all())
```

بالفرونت إند، أضف معامل استعلام `category` لدالة `getRequests()` بملف
`api.ts` وعنصر فلتر `<select>` بملف `RequestsPage.tsx`.

### 5. إضافة حقل جديد (مثلًا `location`، نص حر للغرفة/المنطقة)

- `backend/app/models/request.py` — أضف
  `location: Optional[str] = Field(default=None, max_length=100)`.
- `backend/app/schemas/request.py` — أضف `location: str | None = None`
  لـ `RequestCreateIn` و`RequestOut`.
- `frontend/src/types/index.ts` — أضف `location?: string` لـ
  `SavedRequest`/`ClassifiedProblem`.
- أضف حقل إدخال بملف `ProblemResultCard.tsx` واعرضه بملف
  `RequestsPage.tsx`.
- بما إن جداول SQLite ما تترحّل تلقائيًا للبيانات الموجودة، احذف
  `backend/data/app.db` أثناء عرض مباشر (`Remove-Item backend/data/app.db`)
  عشان يُعاد إنشاؤه بالعمود الجديد — اذكر بصوت عالٍ إن نظامًا إنتاجيًا
  حقيقيًا كان سيستخدم ترحيل Alembic بدل هذا.
